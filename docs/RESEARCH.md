# Research behind the design

What the role asks for, what already exists, and what the documentation says about the limits that shape
the design. Read in October 2026.

## The problem as the job describes it

A payments company connecting Dynamics 365 with its wider platform: Dataverse data models, plug-ins, custom
APIs, model-driven apps and Power Automate; Azure Functions, App Service and API Management in C#/.NET;
REST, the Dataverse Web API and GraphQL with clear contracts, validation and versioning; Kafka with
retries, duplicate messages, schema evolution and reliable synchronisation; OAuth 2.0 with Entra ID,
managed identities and Key Vault; CI/CD with solution packaging, managed solutions, environment variables
and connection references; unit, integration and API contract tests; monitoring. Nice to have: Bicep, PCF,
AI-assisted development. This repository is built around exactly that list, with merchant onboarding as
the domain because that is where a CRM and a payments platform meet.

## What exists already, and the gap

- **Connectors that copy CRM rows into Kafka.** Confluent's Dynamics 365 CRM source connector polls the
  Web API, uses change tracking where enabled and falls back to a `versionnumber` watermark (no deletes);
  delivery is at least once and it is one-way. CData, Airbyte and KingswaySoft offer similar replication.
  They move rows, not intent ("onboarding was requested"), and none writes the platform's answers back.
- **Power Automate flows** calling HTTP endpoints after a save: simple, but a failure after the commit
  loses the change, and there is no ordering or replay story.
- **Samples and tutorials** show a plug-in, a custom API or a Kafka consumer in isolation.

The gap this project fills: a two-way synchronisation whose correctness is shown, not asserted. The
CRM side uses a transactional outbox inside the plug-in pipeline; the platform side applies versioned
aspects so any delivery order converges; both directions are exercised end to end under duplication,
reordering, loss, crashes, contention and throttling, with checks that compare the two systems afterwards.

## Facts the design depends on

| Fact | Source | Where it shows up |
| --- | --- | --- |
| Service protection: per user, 6,000 requests and 1,200 s of execution time in a 5-minute sliding window, 52 concurrent requests; 429 with `Retry-After` from the Web API; codes 0x80072322 / 0x80072321 / 0x80072326 | [Service protection API limits](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/api-limits) | Emulator throttling, the client's Retry-After handling, ADR 3, the throttling drill |
| Batching does not avoid the execution-time limit; start with batches of about 10 | same | One small changeset per event, not large batches |
| Conditional operations: `If-Match` with the row's ETag for optimistic concurrency, `If-None-Match: *` to create only | [Perform conditional operations using the Web API](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/perform-conditional-operations-using-web-api), [sample](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/web-api-conditional-operations-sample) | The applier's changeset; 412 means re-read |
| Retry policies are supported for the Kafka trigger; `-1` retries indefinitely; counts live in instance memory | [Azure Functions error handling and retries](https://learn.microsoft.com/en-us/azure/azure-functions/functions-bindings-error-pages) | `PlatformEventsFunction`, ADR 3 |
| The deployment settings file: `EnvironmentVariables` (SchemaName, Value) and `ConnectionReferences` (LogicalName, ConnectionId, ConnectorId); generated by `pac solution create-settings`, used at import | [Pre-populate connection references and environment variables](https://learn.microsoft.com/en-us/power-platform/alm/conn-ref-env-variables-build-tools) | `alm/settings`, `DeploymentSettings`, the alm workflow |
| The Confluent Dynamics 365 source connector: polling, change tracking or `versionnumber`, at-least-once, JSON only, five entities per connector | [Confluent documentation](https://docs.confluent.io/cloud/current/connectors/cc-dynamics-365-crm-source.html) | The gap above |

## Choices made from these facts

- One request per event where possible, and a small `$batch` changeset where atomicity matters (account,
  terminal, ledger), instead of large batches that hit the execution-time limit.
- Throttling is part of normal operation: the client waits short Retry-After values inline and hands long
  ones back to the consumer, which holds the partition.
- Platform-owned columns are protected by column security, so neither people nor flows can quietly
  overwrite what the platform decides; drift is reported instead of fought over.
- Managed solutions only downstream, with settings per environment checked in CI before an import can fail
  on a missing value.
